# Skill Spec: Cucumber Scenarios

## Goal

Convert any form of acceptance criteria or informal scenario descriptions into
well-formed Gherkin-syntax scenario files, then validate them against the actual
codebase to ensure full coverage — including edge cases and error paths that the
original input may not have mentioned.

---

## Trigger conditions

Invoke this skill when the user asks to:
- "generate cucumber scenarios from this ticket"
- "convert these scenarios to Gherkin"
- "write BDD scenarios for this feature"
- "validate my scenarios against the code"
- "check scenario coverage"
- "create an md file with cucumber scenarios"

Also invoked by the **TDD Orchestrator** agent as Phase 1.

---

## Inputs

| Input | Required | Description |
|---|---|---|
| `input` | Yes | Path to acceptance criteria text, a scenarios file (any format), or raw text pasted inline |
| `targetCode` | No | File glob or directory of the implementation to validate coverage against |
| `outputFile` | No | Where to write the Gherkin output. Default: `.tdd/scenarios.md` |
| `language` | No | Spoken language for Gherkin keywords. Default: `en` |
| `strict` | No | `true` to fail if any scenario cannot be mapped to a code path. Default: `false` |

---

## Behavior

### Step 1 — Detect input format

Inspect the `input` file or text:

| Detected format | Action |
|---|---|
| Valid Gherkin (contains `Feature:`, `Scenario:`, `Given`/`When`/`Then`) | Skip to Step 3 (validation only) |
| Markdown with scenario-like headings / bullet lists | Convert in Step 2 |
| Plain-text acceptance criteria (user stories, JIRA description, prose) | Convert in Step 2 |
| Mixture | Convert non-Gherkin sections in Step 2; preserve existing Gherkin blocks |

### Step 2 — Generate Gherkin scenarios

If conversion is needed, produce a well-formed Gherkin file from the input:

**Mapping rules:**

| Input construct | Gherkin output |
|---|---|
| Feature name / ticket title | `Feature: <title>` block with a `As a… I want… So that…` description |
| Acceptance criterion | One or more `Scenario:` blocks |
| "Happy path" / main flow | `Scenario: <criterion>` with `Given / When / Then` steps |
| "Should not" / error condition | `Scenario: <criterion> — error case` |
| Parameterised cases ("for each X") | `Scenario Outline:` with `Examples:` table |
| Shared precondition across scenarios | `Background:` block |
| @tag hints in input ("admin only", "mobile") | `@admin`, `@mobile` scenario tags |

**Step writing rules:**
- `Given` — system state before the action (existing data, user logged in, feature flag on)
- `When` — the single action being tested
- `Then` — the observable outcome; one assertion per `Then` / `And` step
- No implementation details in steps (no CSS selectors, function names, or database calls)
- Steps must be written in the third person present tense: "the user sees…", "the system returns…"

**Gap detection:**
After generating from the input, inspect `targetCode` (if provided) and add scenarios for:
- Error states (network failure, validation failure, 404) not mentioned in the input
- Boundary values (empty lists, maximum length strings, zero quantities)
- Authentication / authorisation gates visible in the code but absent from the AC
- Any `if` / `switch` branch in the implementation that has no corresponding scenario

Mark auto-generated gap scenarios with `@generated` tag and a comment: `# Generated: not in original AC — review before use`.

### Step 3 — Validate existing Gherkin against code (when `targetCode` is provided)

For each scenario in the file (whether pre-existing or freshly generated):

1. **Step resolution**: for each `Given`/`When`/`Then` step, check whether a matching step definition exists in the project's step-definition files (`.step.ts`, `.steps.js`, `step_definitions/`, `support/`)
   - If a step definition exists: mark as `resolved`
   - If not: mark as `unresolved` — these need implementing

2. **Code path coverage**: map each `When` action to a function or route handler in `targetCode`:
   - Resolved: a function / endpoint name clearly matches the step verb and noun
   - Unresolved: no matching function — flag as a gap

3. **Duplicate detection**: flag scenarios that are semantically identical (same `When` step, same outcome) even if their text differs

4. **Output**: write a `coverage` block at the top of the scenarios file:

```markdown
<!-- coverage: 8 scenarios, 6 resolved, 2 unresolved, 1 duplicate -->
```

### Step 4 — Write output file

Write `outputFile` in this structure:

```gherkin
# Generated by cucumber-scenarios skill — 2026-05-22
# Coverage: 8 scenarios | 6 resolved | 2 unresolved | 1 @generated

Feature: Checkout
  As a logged-in customer
  I want to complete a purchase
  So that I receive my order

  Background:
    Given the user is logged in
    And the cart contains at least one item

  Scenario: Successful checkout with card payment
    When the user submits the order with valid card details
    Then the order confirmation page is shown
    And the order appears in the user's order history

  Scenario: Checkout fails with expired card
    When the user submits the order with an expired card
    Then an error message "Your card has expired" is shown
    And the cart is preserved

  @generated
  # Generated: not in original AC — review before use
  Scenario: Checkout with empty cart
    Given the cart is empty
    When the user attempts to proceed to checkout
    Then the user is redirected to the cart page
    And a message "Your cart is empty" is shown
```

If the input was already valid Gherkin and no changes were made, write the file with the coverage comment prepended and exit without modifying scenario content.

---

## Output structure

```
.tdd/
  scenarios.md          ← Gherkin scenarios (Step 4 output)
```

---

## Edge cases and constraints

- **Input is a URL** (JIRA ticket, Notion page, Confluence): fetch the page content and treat it as plain-text AC; warn if authentication is required
- **Multiple features in one input**: produce a single file with multiple `Feature:` blocks, or split into `<feature-name>.md` files if the features are clearly unrelated — ask the user which to prefer
- **Parameterised steps with unknown values**: use descriptive placeholders in `Scenario Outline` tables (`<user_role>`, `<item_count>`) and add a comment to fill them in
- **Steps that reference UI details**: warn and rephrase to be UI-agnostic (e.g. "the user clicks the Submit button" → "the user submits the form")
- **Code has no test framework**: skip Step 3 code-path coverage check; run Step 3 step-resolution only
- **`strict: true` with unresolved scenarios**: exit with a non-zero status and list every unresolved step
- **Gherkin in a language other than English**: detect from `# language:` comment or `language` input; preserve the detected language in the output

---

## Success criteria

- Output file is valid Gherkin parseable by `@cucumber/cucumber` or `cucumber-js`
- Every acceptance criterion maps to at least one `Scenario`
- Error paths and boundary conditions from `targetCode` are represented (when `targetCode` is provided)
- `@generated` scenarios are clearly annotated
- No step descriptions contain implementation details (CSS selectors, function names, SQL)
- Coverage comment accurately reflects resolved vs unresolved step count
